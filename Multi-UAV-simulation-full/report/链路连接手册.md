## 一、四条物理链路，各管各的

| # | 链路 | 网段 | 干什么 | 介质 |
|---|------|------|--------|------|
| L1 | 飞控 ↔ 机载电脑 | **每架不同**（见下） | uXRCE-DDS，飞控数据的唯一入口 | 网线（点对点） |
| L2 | 机载电脑 ↔ 机载电脑 ↔ 地面 | `192.168.1.0/24` | 机间 ROS2 / 部署 / 监控 | LQ-MESH 电台（无线） |
| L3 | 地面 PC ↔ 仿真机 | 视情况 | 部署代码、取日志 | WiFi 或网线 |
| L4 | 地面 PC ↔ 仿真机（ICS） | `192.168.137.0/24` | 给没有独立网络的仿真机借网 | 网线直连 |

🔴 **L2 和 L4 在地面 PC 上互斥**——笔记本只有一个以太网口。开 ICS 就没有 mesh，
反之亦然。**飞行时必须是 L2**。切换见第五节。

### L1 的两架不一样（最容易踩）

| 机 | 飞控 IP | 机载电脑 IP | 机载电脑网口 |
|----|---------|-------------|--------------|
| **A10** | `10.41.10.2` | `10.41.10.100` | `eno1` |
| **A08** | `192.168.77.2` | `192.168.77.100` | `eno1` |

> 🔴 2026-08-19 现场就因为脚本里写死 `192.168.77.2`，在 A10 上完全没数据
> （`deploy/README.md:147`）。**任何涉及飞控 IP 的脚本都必须按机区分**。
> 飞控侧对应 `AG_IP`（注意 `deploy/README.md` 里那个整数换算的坑：
> `192.168.77.100` 超 int32 上限，须折成负数 `-1062711964`）。

## 二、地址分配（`192.168.1.0/24` mesh 网段）

| 地址 | 归属 | 备注 |
|------|------|------|
| `.100` | 地面 PC / 第二地面站 | `make_mesh_profile.py` 的 PEERS 里预留 |
| `.101` | A10（drone1 机载电脑） | |
| `.102` | A08（drone2 机载电脑） | |
| `.103` | drone3 | 预留 |
| `.123` | 笔记本（现用地面站） | 静态 |
| `.200` `.202` `.203` | **LQ-MESH 电台自身** | 🔴 别占 |

> 🔴 **机载电脑一律 `.10x`，严禁 `.20x`**（2026-08-19 现场定案）。三台电台自己占着
> `.200/.202/.203`，A08 曾被配成 `.202` 造成 IP 冲突。
>
> **冲突的表现极具迷惑性**：同一个 `.202`，从 A10 解析到 Jetson（SSH 正常）、
> 从地面 PC 解析到电台（TCP 被 RST）；ping 两边都通，只有 TCP 露馅；
> `nmcli con up` 发的免费 ARP 还会把归属抢回来，导致 ARP 归属来回翻。
> **判定方法：同一 IP 在不同机器上 `arp -a` / `ip neigh` 比 MAC 是否一致。**
> 危害是飞行中机间 DDS 直接断链，不是"连不上笔记本"的小事。

**改地址的安全手法**（A08 的管理通路只有 mesh 一条，改错=现场只能接显示器救）：

```bash
sudo nmcli con mod lq-mesh +ipv4.addresses <新>/24   # 先加
# 验证新地址 SSH 通
sudo nmcli con mod lq-mesh -ipv4.addresses <旧>/24   # 再删旧
```

且命令要 `sudo setsid` **脱离 SSH 会话**跑——`con up` 会瞬断网卡、必然掉会话，
**掉线 ≠ 没执行**，重连后先查状态再决定要不要重跑。

## 三、DDS 层：物理通了不等于 ROS2 通了

无线多播极不稳，是 mesh"时通时断"的头号原因 ⇒ **跨机 ROS2 发现必须改单播**。

```bash
# 每台各生成一份（只有 --self-ip 不同）
python3 deploy/make_mesh_profile.py --self-ip 192.168.1.101   # 在 A10 上
# → ~/mesh_dds.xml + ~/mesh_dds.env

# 交互 shell
set -a; . ~/mesh_dds.env; set +a
# systemd 则用 EnvironmentFile=~/mesh_dds.env（非交互 shell 不读 .bashrc）
```

`.env` 内容固定为三项：`RMW_IMPLEMENTATION=rmw_fastrtps_cpp` /
`ROS_DOMAIN_ID=0` / `FASTRTPS_DEFAULT_PROFILES_FILE=<xml 路径>`。

### 🔑 接口白名单是必需项，不是可选项

机载电脑同时有 mesh 网卡、飞控直连网卡、WiFi 三张网。不加白名单时 Fast-DDS 会在
**所有**网卡上通告 locator，对端可能挑中路由不到的地址 ⇒
**典型症状是「节点和话题都能发现、就是收不到数据」**。

白名单默认开（本机 mesh IP + `127.0.0.1`）。⚠️ **必须含 `127.0.0.1`**，
否则本机 XRCE Agent 与 mpc_node 互相发现不了。排查时可用 `--no-whitelist` 出对照版。

### 🔑 `ROS_LOCALHOST_ONLY=1` 不能用（2026-08-31 实测确认）

它是 **rmw/rcl 层**的特性，而 **MicroXRCEAgent 不是 ROS 2 节点、直接用 Fast-DDS**，
根本不读这个变量。结果是 Agent 在所有网卡上通告、ROS 节点被关进回环 ⇒ 发现不匹配。
症状：节点全部存活、无任何报错、但一条数据都收不到。

> 证据：`ros2 topic info -v` 里 PX4 话题的发布者显示为
> `Node name: _CREATED_BY_BARE_DDS_APP_`。

## 四、按用途选链路

### 场景 A：纯 SITL（不碰真机）

全部进程在仿真机本机，**不需要任何跨机链路**。

```bash
GZ_IP=127.0.0.1 bash tools/pair2_sitl_check.sh hover
```

🔑 `GZ_IP=127.0.0.1` 让 **gz-transport** 走回环。它和 DDS 是两套东西：
Gazebo 自己的服务发现也用组播、也绑真实网卡，网卡一抖就
`ERROR [gz_bridge] Service call timed out` ⇒ 第二架 PX4 直接起不来。
（2026-08-31 实测：WiFi 抖动期间 px4_1 就是这么失败的。）

⚠️ **仿真机的 px4_msgs 必须是 `release/1.14`**（配 PX4 1.14）。

### 场景 B：台架/地面联调（真机通电、不装桨）

需要 L1 + L2。地面 PC 保持 mesh 静态 `192.168.1.123/24`。

### 场景 C：飞行

需要 L1 + L2，且 **L4（ICS）必须关闭**。

## 五、地面 PC 以太网口的两种状态（互斥，必须手动切）

单口，两种用途只能二选一。两个脚本**都要管理员权限**。

```powershell
# → ICS 模式（给直连的仿真机借网，口变成 192.168.137.1）
powershell -ExecutionPolicy Bypass -File tools/enable_ics.ps1

# → 关 ICS
powershell -ExecutionPolicy Bypass -File tools/enable_ics.ps1 -Off

# → 还原 mesh 静态配置（192.168.1.123/24，网关 .1，DNS 8.8.8.8）
powershell -ExecutionPolicy Bypass -File tools/restore_mesh_nic.ps1
```

🔴 **飞行前必须 `-Off` 再 `restore_mesh_nic.ps1`**。ICS 会把该口从
`192.168.1.123/24` 改成 `192.168.137.1`，此时地面 PC 与整个 mesh 断开。

⚠️ 关 ICS 会让靠它借网的仿真机断网——**先把仿真机切到它自己的网络，再还原**。

## 六、连接顺序（真机，从全部断电开始）

1. **先 Jetson，后飞控**（上电顺序，见 `jetson-orin-nx-bench` 记忆）。别硬拔 Jetson 电源（NVMe 损坏风险）。
2. **UTC 对时**：`sudo date -s ...`。两台 Jetson 无 RTC 电池、现场无 NTP，
   开机时间是 1970。
   > 不影响飞行安全（邻居新鲜度判定用的是本机时钟的经过时间，跨机偏差进不来），
   > 但**会毁掉数据归档**——CSV/rosbag 文件名全变 1970，而飞控 `.ulg` 拿到 GPS 后是
   > 真实时间，两边对不上。
3. **查 IP 冲突**：`arp -a` / `ip neigh` 比对同一 IP 在不同机器上的 MAC。
4. **起 DDS 环境**：每台 `set -a; . ~/mesh_dds.env; set +a`。
5. **分级预检**：`python3 tools/check_mesh_dds.py`
   - A 环境变量 → B profile 自洽 → C 本机 mesh 地址 → D ping →
     E 电台地址冲突 → F 跨机 ROS2 发现 → G 真收发一条消息
   - 双机联调：一台 `--sub`，另一台 `--pub --expect-peer A08`
   - 🔑 **F 通而 G 不通 = 上面那个多网卡 locator 问题**
   - 🔑 一律 `--no-daemon`（ros2 daemon 会缓存、报出早已消失的节点）
6. **部署 + build**：`bash tools/deploy_to_jetson.sh A10 A08`，然后每台
   `colcon build --packages-select mpc_control`。**不 build 装的还是旧的。**
7. 之后进 `report/室外RTK_offboard流程.md`。

## 七、验证命令速查

| 查什么 | 命令 | 期望 |
|--------|------|------|
| 物理链路 | `cat /sys/class/net/eno1/carrier` | `1` |
| 本机地址 | `ip -br addr` | 见第二节地址表 |
| IP 冲突 | 各机 `ip neigh` 比 MAC | 同一 IP 的 MAC 一致 |
| DDS 全链 | `python3 tools/check_mesh_dds.py --no-daemon` | A–G 全绿 |
| 话题真有数据 | `ros2 topic echo --once --qos-reliability best_effort <topic>` | 有输出 |
| 部署版本 | `cat ~/Multi-UAV-simulation/DEPLOYED_VERSION` | 与上游 hash 一致 |

🔑 **`ros2 topic echo` 必须加 `--qos-reliability best_effort`**：PX4 的 out 话题是
`BEST_EFFORT`，而 echo 默认按 `RELIABLE` 订阅 ⇒ 不兼容、一条都收不到，
**症状与"根本没数据"完全一样**。（2026-08-31 因此白查了一整轮。）

## 八、已知陷阱汇总

| 陷阱 | 症状 | 处理 |
|------|------|------|
| `ros2 topic echo` QoS 默认 RELIABLE | 读空，与"没数据"无法区分 | 加 `--qos-reliability best_effort` |
| 多网卡无白名单 | 发现得到、收不到数据 | 白名单（含 `127.0.0.1`） |
| `ROS_LOCALHOST_ONLY=1` | 节点全活、零数据、无报错 | **别用**，Agent 不吃这套 |
| 电台占 `.20x` | ping 通但 TCP 被 RST；ARP 归属来回翻 | 机载电脑用 `.10x` |
| gz-transport 组播 | `gz_bridge Service call timed out`，第二架起不来 | `GZ_IP=127.0.0.1` |
| PX4 陈旧锁 | `PX4 server already running`，静默退出 | `tools/cleanup_sim.sh`（已含清理） |
| px4_msgs 版本不符 | 类型哈希不同，DDS 不匹配，不报错 | SITL 用 1.14 / 真机 1.16，**两个工作区** |
| ros2 daemon 缓存 | 报出早已消失的节点 | `--no-daemon` 或先 `ros2 daemon stop` |
| 非交互 SSH 不读 `.bashrc` | `mpc_node` 静默崩溃（找不到 `libhpipm.so`） | 用 `.env` + 显式 `export` |
| `pkill -f` 经 ssh 内联 | `exit 255`，后半段静默不执行 | 杀进程与验证拆成两条独立 ssh |
